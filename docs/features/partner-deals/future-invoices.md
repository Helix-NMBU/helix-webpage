# Future-season invoice tasks

Won cash contributions without invoice tasks appear as planned on the agreement. The server-only runner considers a contribution due when its season starts according to the Oslo calendar, then creates an invoice task in the configured current working season and links it to the contribution's own season. This makes a missed task visible to Finance after a later rollover while preserving the season being invoiced. It uses a transaction lock and unique deal/season link; a retry does not duplicate tasks. A failed item remains unlinked, is returned as a failure, and is retried on the next run. Product and service contributions do not create invoice tasks.

No scheduler, secret or production configuration is installed by this change. Before relying on automation, an authorized operator must:

1. Provision each future finance season with `finance.provision_future_season(operator_member_id, code, name, start_date, end_date)`. The operator must hold the platform-administrator role. The function preserves the current-season setting, rejects overlapping dates with the current season, and records a finance audit entry.
2. At rollover, explicitly configure the new finance current season using the existing operator workflow. Then call `project_management.provision_current_departments(operator_member_id)` for that current season. It creates empty department records and does not transfer any member permissions. Use member access administration to grant the current Finance team access and a lead. Ensure the season dates cover the current Oslo date and the season is not closed.
3. Store a long random secret, at least 32 characters, as server-only `PARTNER_INVOICE_RUNNER_SECRET`. Configure an external scheduler to POST to `/api/partner-invoice-runner` with `Authorization: Bearer <secret>`. Vercel's GET-only cron configuration is not sufficient for this POST endpoint. Configure monitoring and retry for non-200 responses; HTTP 503 means setup failed or at least one item needs retry. Do not put the secret in source, logs or a browser.
4. Test the scheduled call and inspect its `created`, `failed`, and `failures` result with authorized synthetic local data before production use. The same authenticated POST is the manual retry path. Failed contributions remain due and a later run catches them up.

The migration rejects overlapping existing season date ranges, so an operator must reconcile any overlap before applying it. Invoice creation requires a verified, active Finance lead in the current season; unassigned Marketing deliverables require a verified, active Business & Marketing lead; an empty or revoked Finance roster leaves the work due and reports a failure. Current-season settings are locked during task creation.

The migration changes project-management reads, mutations and authorization to use the configured current season. Historical task rows remain stored; the normal workspace shows the current working season. No member roster is copied automatically, and the scheduler will not create inaccessible tasks when the current season or Finance department is missing.

A due invoice paused by a pending agreement change is returned as a failed item with code `agreement_change_pending`, so monitoring does not mistake it for a successful empty run. After the change is reconciled, a later run creates the task. A contribution explicitly recorded as handled manually is not treated as an automatic task failure.
