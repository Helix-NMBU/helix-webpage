# Project purchase contract (PBA-05)

Project registration uses the existing `/api/finance` entry point. `projectPurchaseContext` is a scoped GET with `projectId` and optional `responsibleDepartmentId`. It returns authorized systems and effective approved entries. A mapped, genuinely approved legacy entry remains selectable while its first project candidate is under review. A newly drafted entry is unavailable until project approval.

Scoped POST actions are `checkProjectPurchase`, `authorizeProjectPurchaseUpload`, `finalizeProjectPurchaseUpload` and `registerProjectPurchase`. Bind each action to `projectId` and `responsibleDepartmentId`. Registration also supplies a stable request ID and the existing `PurchaseInput`. Quantities describe the order; amountNok is each line's total. Ordinary department leads never receive broad Finance read capabilities.

Migration070 adds dedicated scoped registration/upload routines. They recheck active Neon/Google identity and current department assignments under locks. Lock order is project header, project/authority/season, approved candidate, optional request, ordered allocation anchors, then the season ledger and counters. Existing generic Finance registration and void functions wrap their retained request/payment logic with the same header order, deriving affected headers from authoritative allocation and request items.

A cost outside the approved plan remains an actual expense. An absent season ledger is created as Draft without approval metadata. `unbudgeted` and `budget_overrun` exception reviews retain the original discrepancy, including original approved version or genuine legacy budget/date. Purchase lines retain stable allocation identity, `project_budget_id` and `approved_version_id`. `budget_authority` distinguishes project approval, genuine legacy approval and unbudgeted costs. Legacy approval never receives an invented project version ID. Existing imported purchases remain untouched.

`setProjectBudgetCompletion` uses a dedicated SQL routine with the header revision, stable entry ID, boolean complete and mandatory reason. A registered purchase is required before completing an entry. Completion is independent of amount and payment. Further registrations and linked voids clear completion with audit evidence. Read projections use purchase existence, including a zero net actual, for partial state.

## Evidence seam for PBA-06

The upload executor retains owned staging/final keys, immutable byte verification, SHA256 checks and the final-candidate cleanup ledger. Scoped uploads retain their project and responsible department. Each registration creates its own existing `finance.documents` records and links consumed upload IDs to exactly one purchase. Document IDs, purchase IDs/public references and private storage keys remain stable inputs for Drive transfer; expense persistence does not depend on a Drive provider. This slice adds no Drive API calls. Historical private-storage evidence remains compatible with the existing document endpoint.

## UI and local verification

`ProjectBudgetPurchases` accepts optional `budget`, or `projectId` plus `responsibleDepartmentId`, `onChanged`, and `onDirtyChange`. It always loads effective entries itself. The project-budget panel renders it for authorized detail scopes regardless of which budget version is displayed. Authorized scopes without a visible header have a project selector for incurred costs. Finance's existing purchases page uses `ProjectPurchaseLauncher` ahead of the retained optional-request/legacy form.

Dedicated loopback fixtures share `helix-project-budgets-local-v1` and store purchase evidence metadata/audit in `helix-project-purchases-local-v1`. Use member-local mode, sign in, and select `budgetRole=project_lead`, `department_lead`, `finance`, or `head_of_finance`. Example project: Chassis & assembly; responsible department: Mechanical & Production. Start with department_lead and no budget to record an unbudgeted incurred cost. For approved-entry checks, create a budget/entry as project_lead, submit, approve as department_lead, and finally approve as head_of_finance. Switch back to department_lead, register two partial orders with separate invoice files, mark complete with a reason, then register another order to reopen. Finance can select projects from its purchases page. The selected role never grants production access.

Same-project refreshes retain entered fields. Scope/session changes clear private input. Ambiguous registration and completion responses retain the original request ID and snapshot for retry. Rapid submits are synchronously guarded. Shared Radix dialogs/selects provide pointer/keyboard behavior and opener-focus recovery; notifications report saved actuals and Finance review warnings.
