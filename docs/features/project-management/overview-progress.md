# Overview progress and milestones

User request, 26 October 2026: replace Overview's four summary cards with a Linear-inspired progress graph and show milestones with completion progress. Reference screenshots show Scope, Started, Completed, an assignee breakdown, and milestone percentages. This extends the current Project Management feature on `codex/project-management`; no publishing or production migration is authorized.

## Behavior

- Overview has a full-width progress graph in place of its four summary cards, followed by Projects and Upcoming Milestones widgets. Area pages retain their summary cards. My tasks stays a personal list.
- Scope is the number of non-cancelled task-kind records. Started includes In progress, Blocked and Done. Completed is Done. Milestones are excluded from these counts. Every task has equal weight.
- Lines show end-of-day recorded states in Europe/Oslo, carried forward after the first observation. There is no inferred earlier history and no forecast. Future space is shaded. A screen-reader table exposes each recorded day's values; the visible data disclosure is removed.
- The fixed Areas section shows completion by the departments assigned to projects. Shared-project tasks count toward each participating department and once in overall scope. Known departments with no tasks show zero progress; work without an allocated department appears under No department. There is no Assignees view or breakdown switch.
- A milestone is a dated goal, using the existing milestone task kind. The confirmed hierarchy is Season → Project → Milestone → Task, currently S27. Every new milestone requires a department-level project; every new task requires a milestone and inherits that goal's project. Parent and child must match season, project and work area. Milestones cannot nest.
- A milestone's percentage is completed linked tasks divided by non-cancelled linked tasks. An empty goal shows 0% of 0. Its status and deadline remain separate from its child-task completion; finishing tasks does not silently close the goal.
- Selecting a project in the Overview widget opens its work-area page, filtered to all its tasks including completed work. Prior search and milestone filters are cleared. Projects use the Tabler cube icon and show completion from their non-cancelled tasks. Needs organization opens a separate work queue with task details and scoped Organize actions. Selecting a milestone within a project shows its linked tasks, including completed work. Needs organization shows pre-existing work without a valid project/milestone chain. The user explicitly chose to preserve that work until a Department Lead places it; no placeholder projects or milestones are generated. Work-area project cards expose expandable milestones and their child tasks, preserving the season/project/milestone/task structure. Overview omits these duplicate project cards, the department progress cards and the latest-deadline summary, placing Upcoming Milestones directly after the Projects widget.
- Department Leads create and edit milestones and task links in their authorized work areas. Overview's project controls are available to members with project-management access; task and milestone creation remains in authorized work areas. Personal and Overview details retain status-only editing.
- Legacy work remains readable and status-updatable. Full detail saves require placement in the hierarchy; Overview's Organize action navigates a scoped Lead to the proper work area. Existing links to a cancelled goal remain; new links to a cancelled goal are rejected. Changing a goal's type, area or project must not invalidate child links.

Overview has no manual Refresh button. Task mutations replace the workspace immediately; opening a Project Management route reloads the workspace. The Areas helper sentence and visible View progress data section are removed.

Overview's table is an Upcoming Milestones widget: only open milestone-kind records due from today through day 30, inclusive, using the Europe/Oslo date. Past, undated, completed and cancelled milestones and ordinary tasks are excluded. It sorts by earliest target date with title as tie-breaker. Columns are Milestone, Department, Priority, Leads, Target date, Tasks and Status. Department comes from the linked project and lists all participating departments; unallocated work shows No department. Milestone names have no subtitles or metadata underneath. Upcoming priority cells use Tabler signal-bar icons for Low/Normal/High and an exclamation-circle icon for Urgent, with accessible labels and tooltips. Target dates have a calendar icon and omit the year in visible text; their full date remains in the time element and tooltip. Tasks shows completed/total linked tasks; Status shows a circular progress ring and percentage. Counts use all linked non-cancelled tasks, regardless of child deadlines. An empty state appears when no milestones qualify. There are no task filters or List/Timeline switch in this widget.

Work-area pages retain the full Tasks & milestones list, earliest deadline first and undated work last, with project/milestone/status filters and Timeline. Milestones there also show circular task-completion progress; their recorded state remains editable in details.

Upcoming Milestones provides inline menus for priority, Leads and target date to Department Leads authorized for that milestone's area. Milestones must be organized before detail edits; Needs organization remains the placement path for legacy work. Priority saves on selection; Leads supports searching existing members, multiple selections, Clear, Cancel and Save, without invitations. Target date offers a date input, month navigation and keyboard-accessible day grid, with Cancel and Save. A changed deadline can move a goal out of the 30-day widget. These edits use the existing full-save API, revision checks and validation, preserving every other task field. Failed saves keep drafts open and report recovery through shared notifications.

Milestones support multiple Leads through the existing multi-member assignment list, with Lead labels in creation, editing and avatar descriptions. Tasks retain multiple assignees. These are milestone ownership assignments; they do not grant Department Lead permissions. Only the existing authorized area Leads can edit assignments, and assigned members retain status updates.

## Persistence and validation

Migration 013 enforces the strict hierarchy for new records, association changes and full saves while preserving unchanged legacy records and their status updates. Migration 012 adds the milestone relation and immutable task-state events. The baseline records existing state at migration time. Later inserts, relevant state changes and deletions add observed events in the same transaction as the change. Scheduled dates and old completion timestamps do not create history. Database locking serializes task relation changes; failed edits roll back both data and events. Existing identity, access, Lead authorization and revision checks remain in force.

The API includes explicit nullable `milestoneId` and ordered `progressEvents`. Old detail-save payloads lacking `milestoneId` are rejected to avoid clearing links from stale tabs. Deploy the migration, API and client together and reload older tabs. Dedicated loopback fixtures upgrade existing data with a present-time baseline and no automatic milestone links; fresh fixtures include known synthetic activity and linked goals for local checks.

Run focused model, local repository, UI, API and database integration tests; all three typechecks, lint and build. Inspect graph, empty state, milestones, linking, completion changes and creation navigation in the browser. Real Neon migration, real Google login and production release remain separate operator steps.

## Platform icons

The user requested Tabler icons across the whole platform. Use the official `@tabler/icons-react` package and Tabler component names in navigation, controls and feature UI. Milestones use `IconDiamonds`; Tasks uses `IconCheckbox`. Preserve existing accessibility labels, hide decorative control glyphs from assistive technology, and keep branding and chart geometry separate from UI icons. The shadcn configuration also selects Tabler for future components.
