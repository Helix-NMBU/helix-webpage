# Project management setup

The member platform uses `/project-management/overview`, `/project-management/production`, `/project-management/partnership-deliverables`, `/project-management/marketing`, `/project-management/operations`, and `/tasks`. Legacy Mechanical & Production section links redirect to Production.

## Local development

Keep credentials in the existing untracked `.env.local`. Run `npm run dev:member` and open `http://127.0.0.1:5190/project-management/overview`. The dedicated `member-local` mode provides local accounts and project fixtures. Its tasks persist in browser local storage under `helix-member-local-projects-v1`; removing that key resets only the project fixtures. These fixtures do not call Neon and cannot be enabled in a production build or on a non-loopback host.

The regular development server uses `/api/projects`, which rewrites to the shared `/api/member-login?__module=projects` entrypoint to avoid adding a Vercel function. The project handler uses the existing member session and `DATABASE_URL`. It does not accept fixture tokens. Use an isolated Neon database branch to validate real authentication and persistence. Never point schema setup at production as part of a local UI check.

## Database and authorization

Migration `db/migrations/009_project_management.sql` adds the `project_management` schema, access grants, projects, tasks, and a transactional mutation function. Migration `010_department_lead_tasks.sql` adds the explicit Department Lead task permissions. Migration `011_task_assignees.sql` moves assignment into `project_management.task_assignees`, backfills existing single-person assignments, and removes the old `tasks.assignee_id` column. Reapplying it preserves the current assignments. Apply migrations through the existing `npm run neon:setup` workflow, using a direct database connection in an untracked environment file. Inspect pending migrations before applying them to an isolated database.

An authenticated Helix Google account also needs an explicit active row in `project_management.access`. The migrations create no accounts or access grants. Grant initial department leads and selected members through the trusted database operator, using the existing `identity.members.id` as `member_id`. `active = true, can_manage = true` grants project management and status updates. It does not authorize task creation, detail editing or assignment. Those actions require an explicit Department Lead feature grant in `task_lead_categories`, an array of the authorized work areas: `production`, `partnership-deliverables`, `marketing`, `operations`. Issue these permissions only to Department Leads, with the areas appropriate to their responsibilities. The new column defaults to an empty array, preserving a closed permission boundary for existing management accounts. A Lead can hold a task grant without project-management permission.

Members with an active module grant can see shared progress and update their assigned task statuses. A Lead can also update statuses in their authorized areas. Every mutation rechecks current access and Lead permissions in the database while holding the grant row against concurrent revocation. Browser role titles and partner OTP sessions do not grant module access. Migrating the schema does not add real Lead grants; those remain an explicit trusted-operator step.

My tasks is a compact personal work list with shared status controls. Its view settings and icon-only Refresh control sit beside the page heading. It contains only task records assigned to the authenticated member, even when that member leads a milestone. Its settings icon opens a shadcn menu for List/Board switching, grouping, ordering, area/status/project/milestone filters, completed/cancelled visibility and display properties. Optional columns include linked milestone, project, due date, assignee, priority and partner. Milestone links open the project with that milestone filter. Preferences use URL parameters and survive reloads and returning from task details. Board groups cards by status while retaining the saved List grouping. Display-property toggles apply to cards as well as table columns. The list has no creation or assignment controls, including for Leads. Overview likewise has no task creation or assignment editor. Department Leads use New task in the authorized Project Management subfolder. The compact composer fixes that area and offers an optional description, due date, assignees, project, extra details and Create another. Assignment and detail editing of existing tasks also happen in those subfolders.

Only the trusted server database owner can read and mutate the module tables. Browser database access is not exposed. Assignment choices return eligible members' IDs, names and optional authentication-profile image URLs, without private CV data. The existing shadcn Avatar components show profile photos with initials as the fallback. Task rows show overlapping avatars, with an overflow count for larger groups. Each mutation includes the saved revision; a conflicting edit returns HTTP 409 and retains the editor's unsaved input. Reload the task list, close the editor, and reopen the item to review the saved version before reapplying edits.

Tasks accept up to 20 assignees in an `assigneeIds` array. The searchable assignment picker supports selecting and removing people without replacing the other selections. A shared task appears in every assignee's My tasks list; any current assignee can complete or reopen it, updating one shared status for everyone. Removing an assignee removes their own-task update permission. Lead permissions still control assignment and detail editing. Existing local fixture assignments upgrade in place.

Deploy migration 011, the API and the client together. Older single-assignee API payloads are rejected so a stale client cannot silently clear co-assignees; reload old browser tabs after release. Migration 011 has not been applied to a real Neon database during local validation.

Migration `012_project_milestones.sql` adds task-to-milestone links and observed task-state history. Existing tasks receive a baseline at migration time; dates from before that baseline are not reconstructed. Every relevant task mutation records a new observation atomically. The API requires an explicit nullable `milestoneId` and returns ordered `progressEvents`. Deploy migration 012 with its API and client, then reload older tabs. No live migration was performed in this implementation run.

## Progress and scope

The first release is scoped to S27. Projects belong to the season and can list multiple participating departments; milestones and tasks are nested beneath them. A milestone is a task record with type `milestone` and a required deadline. The hierarchy is S27 → Project → Milestone → Task. New milestones require a project, and new tasks require a milestone in that project and work area; the task inherits the project from its milestone. Migration 013 enforces this on new records and full saves. Existing ungrouped records remain in Needs organization, with status updates still available until a Department Lead places them. No placeholder projects or milestones are created. Progress is the percentage of non-cancelled linked tasks marked Done, independent of the goal's own status. Department Leads create milestones and manage links in their authorized work areas; Overview's add control navigates to the selected area. Completion is completed task-kind records divided by all non-cancelled task-kind records. Milestones are tracked separately through their status and deadline. Shared project tasks contribute to each participating department's progress.

Overview replaces its four summary cards with a recorded Scope/Started/Completed graph, a fixed Areas section showing completion by project department, and a milestone list below the full-width graph. Expand a project's milestones to see its tasks. Started includes in-progress, blocked and completed task-kind records; Scope excludes cancelled records and milestones. Selecting a milestone filters its linked tasks, including completed work. History starts at the first observation and the shaded future has no forecast. See `overview-progress.md` for the full behavior.

Dates use calendar days in Europe/Oslo. Open tasks and milestones before today are overdue. Deadlines from today through seven days ahead are approaching. Closed and cancelled work does not count toward urgency. The timeline displays recorded start dates and deadlines; it does not model dependencies, effort or available team capacity. The last open deadline describes the current schedule rather than predicting completion.

Partnership deliverables record obligations by sponsor/partner name, with delivered and outstanding counts and a searchable list. Both completed and outstanding obligations appear by default. Sponsor imports, tier checklist generation and completeness against actual S27 agreements remain pending the confirmed Attio and benefit mappings. No sponsor obligations are inferred from a tier or imported from legacy data.

## Validation

Run `npm test`, `npm run typecheck`, `npm run typecheck:api`, `npm run typecheck:api:runtime`, `npm run lint`, and `npm run build`. Database tests use isolated PGlite instances, not a live Neon project. The full suite starts loopback HTTP servers and needs permission to listen locally. Inspect creation, assignment, status changes, personal task filtering, delivery counts, timeline navigation and reload persistence in the browser. Local fixture checks and database integration tests do not establish that a hosted Neon migration or real Google sign-in has been exercised.

Publishing, migration of a production database, and deployment require user authorization.


Migration `014_milestone_field_updates.sql` adds the `update_milestone` operation for priority, multiple Leads and target dates, including unorganized legacy milestones. Apply it before releasing the corresponding API/client. It preserves existing placement, task links, status and history; full saves and new records still require organization. Test locally with the project-management database suite before an authorized production release.


Migration `015_project_departments.sql` adds platform-managed S27 departments and memberships. Project managers (`can_manage`) configure them from Areas; ordinary members and scoped task Leads have read-only access to that management surface. A department Lead must be one of its members. These records do not change task-area feature grants. Existing project department names can be configured in place, and names remain stable after creation. No public website roster is imported. Apply migration 015 before releasing the updated API/client.


Migration `016_fixed_departments.sql` limits departments to Management, Mechanical & Production, Electronics, Software & Autonomous, Business & Marketing, Logistics and Finance. It creates the fixed records without assigning members, maps recognized old names and project associations, and preserves original metadata in private backup tables. Merged departments keep the union of members; if prior Leads disagree, a manager must select the Lead. Membership editing remains manager-only, department creation is rejected, and project department values are constrained to the catalog. Apply migration 016 before releasing the corresponding API/client.


Migration `017_workspace_directory.sql` adds member-directory revisions and recorded last-seen timestamps, plus project priority and multiple project Leads. Apply it after migration 016 before releasing the workspace navigation/API. The Members, Projects and Departments directories are available to verified Google Workspace members without a task-module grant; directory responses omit email, CV and authentication identifiers. Last seen records workspace API activity at most every five minutes, not live presence. Missing history remains blank.

The existing server-owned Admin role controls member name, Helix-title and department edits. This page does not grant platform roles, recruitment permissions or task-module access. Member and department revisions protect concurrent edits; an existing department Lead must be removed before assigning another. Project managers retain department editing from Areas, including memberships without a task-module grant. Project managers can create/edit all projects; department Leads can create/edit projects involving a department they lead. Being a platform Admin or a task-area Lead alone does not grant project creation. Project priority and up to twenty Leads persist independently of milestone Leads. Task and milestone permissions remain unchanged.

The workspace API uses `/api/member-login?__module=workspace`, consolidated into the existing authenticated member function. No new Vercel function or public website route is added. Local fixtures share the existing project/department store and remain gated by member-local mode on loopback. No live migration, role change, publication or deployment has been performed.


Migration `018_department_homes.sql` adds private department descriptions and shared Google Drive folder links with independent optimistic revisions. Only current verified department members can read these settings; only the department Lead or a platform admin who is also a member can edit them. Membership edits and settings writes share the department advisory lock. Directory responses do not contain the folder links. The handler uses the existing workspace module with `department=<uuid>` for reads and `save_department_home` for writes, preserving the function budget.

Both department entry points now open Overview, Documents and Members tabs. The page has member/Lead avatars and a Projects quick link filtered to the department. Documents stay in the shared Google Drive. This implementation saves a folder link and opens it in Google Drive, whose sharing rules still apply. It does not request Drive OAuth permissions, enumerate files or represent a folder link as an authenticated Drive connection. An in-platform Google Drive connection remains follow-up work. Apply migration 018 before releasing the API/client; no live migration or deployment has been performed.


Migration `019_department_settings_permissions.sql` adds active project managers (`project_management.access.can_manage`) to department-settings editors. The department head (stored as the department Lead) and platform admins retain access. Every editor still needs department membership and a verified Helix Google identity. Task-area Lead grants and role-title text alone do not grant settings access. Writes lock the manager grant against concurrent revocation. Apply migration 019 before releasing this permission change.
